# Git Secret Scanner Release Design

## Цель

За три дня выпустить первую полезную версию `git-secret-scanner` — небольшую
кроссплатформенную CLI утилиту, которая проверяет подготовленные к коммиту
изменения и блокирует попадание секретов в Git. История репозитория должна
состоять из небольших, законченных и проверяемых изменений, а не из пустых
коммитов ради графика активности.

## Выбранный подход

Разработка идёт коротким трёхдневным спринтом. В конце третьего дня публикуется
GitHub Release `v0.1.0`. После релиза проект можно поддерживать небольшими
обновлениями либо сразу перейти к следующему мини-проекту.

Плановый результат:

- 15–20 содержательных коммитов;
- три активных дня на GitHub;
- одна готовая CLI утилита;
- автоматические тесты и сборки;
- публичный релиз с бинарниками и понятным README.

## Технологии

### Go

Основной язык проекта. Go подходит для CLI утилиты, потому что быстро
компилируется, имеет хорошую стандартную библиотеку и позволяет выпускать один
исполняемый файл без внешнего runtime. Один исходный проект можно собирать для
Linux, macOS и Windows.

### Стандартная библиотека Go

Используется для запуска Git, разбора аргументов, регулярных выражений,
вычисления энтропии, JSON-конфигурации и форматирования вывода. Дополнительные
зависимости подключаются только там, где они заметно уменьшают сложность.

### YAML и JSON

Проектная конфигурация хранится в `.secret-scanner.yaml` с запасным вариантом
`.secret-scanner.json`. YAML разбирается через `gopkg.in/yaml.v3`, JSON — через
стандартную библиотеку. Парсер работает в строгом режиме: неизвестное поле,
неверный тип или некорректное регулярное выражение завершают проверку кодом `2`.

Для `scan --staged` конфигурация по умолчанию читается из Git index, а не из
рабочего дерева. Порядок выбора: явный `--config`, индексная
`.secret-scanner.yaml`, индексная `.secret-scanner.json`, встроенные значения.
Явный `--config` считается осознанным внешним источником и отмечается в verbose
выводе. Если оба стандартных файла находятся в индексе, YAML имеет приоритет и
выводится предупреждение. Ошибка найденного конфигурационного файла не приводит
к откату на дефолты.

### Git CLI

Сканер получает staged diff и контекст только из Git index. Файлы рабочего
дерева при staged-проверке не читаются, поэтому частичное добавление через
`git add -p` обрабатывается правильно.

Сначала определяется корень через `git rev-parse --show-toplevel`; все следующие
команды запускаются из него с `GIT_LITERAL_PATHSPECS=1`. Список файлов получается
через `git diff --cached --name-status -z --diff-filter=ACMRT`. Каждый путь
передаётся в `exec.Command` отдельным аргументом без shell-интерполяции. Для
Для контекста и проверки типа scanner сначала вызывает literal
`git ls-files --stage -z
-- <path>`, требует единственную запись stage `0`, извлекает mode и object ID и
читает staged blob через `git cat-file blob <oid>`. Путь никогда не встраивается
в revision expression. Blob с NUL блокируется кодом `2` до построения patch.
После классификации текстового blob вызывается `git diff --cached --text
--no-ext-diff --no-textconv --no-color --unified=0 -- <path>`. Флаг `--text`
не позволяет `.gitattributes -diff` скрыть staged-текст как binary diff, а
literal pathspec mode не позволяет имени вида `:(exclude)*` изменить смысл
команды. Парсер принимает только строки `+` внутри корректного hunk, игнорирует
заголовок `+++`, а номер строки вычисляет из правой части `@@`.

Поддерживаются initial commit, переименования, type
changes, CRLF, пробелы и необычные символы в путях. Текстовый regular blob
сканируется; binary blob с NUL, symlink и submodule блокируются кодом `2`, если
путь явно не исключён конфигурацией. Ошибка Git, некорректный patch или
неоднозначное состояние также завершают проверку кодом `2`.

### Go testing

Встроенный пакет `testing` используется для unit-тестов, интеграционных тестов
во временных Git-репозиториях и benchmarks. Цель тестов — подтвердить
правильность, безопасность вывода и приемлемую скорость, а не получить высокий
процент покрытия любой ценой.

### GitHub Actions

CI запускает форматирование, тесты и сборку на Linux, macOS и Windows. Отдельный
release workflow собирает архивы и прикрепляет их к GitHub Release по тегу.

### GoReleaser

Используется на этапе релиза для воспроизводимой кроссплатформенной сборки,
контрольных сумм и публикации артефактов. Если его настройка не укладывается в
третий день, `v0.1.0` выпускается через простой GitHub Actions matrix, а
GoReleaser переносится в `v0.1.1`.

## Архитектура MVP

Проект разделяется на небольшие модули с одной ответственностью:

- `cmd/git-secret-scanner` — CLI и коды завершения;
- `internal/gitindex` — staged diff, строки и номера строк;
- `internal/rules` — встроенные и пользовательские regex-правила;
- `internal/entropy` — токенизация, классификация и энтропия Шеннона;
- `internal/scan` — единый конвейер обнаружения;
- `internal/config` — YAML и JSON конфигурация;
- `internal/report` — уровни риска, маскирование и безопасный вывод;
- `internal/hooks` — установка и удаление pre-commit hook.

Поток данных:

1. CLI загружает и проверяет конфигурацию.
2. Git-модуль получает только добавленные staged-строки.
3. Сканер применяет ignore и allowlist.
4. Regex-правила ищут известные секреты.
5. Entropy-модуль анализирует оставшиеся кандидаты.
6. Reporter маскирует все найденные значения до вывода.
7. CLI возвращает `0`, `1` или `2` по утверждённой семантике.

## Границы релиза v0.1.0

В первый релиз входят:

- команда `scan --staged`;
- анализ только добавленных строк из Git index;
- пять встроенных правил: AWS, GitHub, private key, Slack webhook и JWT;
- энтропия для Hex, Base64 и printable ASCII;
- `.secret-scanner.yaml` и запасной JSON-конфиг;
- allowlist и директива `secret-ignore`;
- безопасное маскирование совпадений без вывода исходных snippets;
- exit codes `0`, `1` и `2` с fail-closed на системных ошибках;
- команды `install`, `uninstall` и `version`;
- unit- и интеграционные тесты;
- CI и бинарники для Linux, macOS и Windows;
- README с установкой и короткой демонстрацией.

В последующие релизы переносятся дополнительные правила, пакетные менеджеры,
SARIF/JSON-отчёты, сканирование директорий и истории Git, GUI и серверный режим.

## Контракты безопасности

### Обнаружение и подавление

Каждое встроенное и пользовательское правило возвращает точный диапазон
секретного значения, а не диапазон всей строки. Правила `v0.1.0`:

- AWS Access Key ID: `(A3T[A-Z0-9]|AKIA|AGPA|AIDA|AROA|AIPA|ANPA|ANVA|ASIA)[A-Z0-9]{16}`;
- GitHub token: `gh[pousr]_[A-Za-z0-9]{36,255}` или
  `github_pat_[A-Za-z0-9_]{22,255}`;
- private key header: `-----BEGIN (RSA |EC |OPENSSH |DSA )?PRIVATE KEY-----`;
- Slack webhook: полный URL вида
  `https://hooks.slack.com/services/T…/B…/<token>`;
- JWT: три непустых Base64URL-сегмента, разделённые точками, первый начинается
  с `eyJ`.

У первых четырёх правил уровень HIGH; JWT имеет MEDIUM из-за частых тестовых
значений. Regex-rule захватывает только значение целиком. Каждое правило имеет
положительные, отрицательные и redaction-тесты.

Entropy-анализ ограничен токенами длиной до 512 символов и использует порядок:

- HEX: `^[0-9a-fA-F]+$`, минимум 32 символа, порог `3.6`;
- BASE64: `^[A-Za-z0-9+/=]+$`, минимум 20 символов, присутствуют upper, lower
  и digit либо `+`/`/`, порог `4.7`;
- PRINTABLE ASCII: непрерывный токен без пробелов, минимум 16 символов,
  порог `5.1`.

Entropy-only finding имеет MEDIUM. По умолчанию MEDIUM выводится как warning и
не блокирует; `block_on_medium_risk: true` превращает его в код `1`.

Allowlist проверяется до формирования отчёта. Она поддерживает точные тестовые
значения, регулярные выражения и SHA-256 fingerprints; fingerprints рекомендуются
для любых непубличных значений. Next-line suppression распознаётся только когда
вся предыдущая staged-строка после trim равна `// secret-ignore`,
`# secret-ignore`, `// nosecret` или `# nosecret`. Same-line suppression
распознаётся только как такой же отдельный trailing-комментарий после найденного
значения и перед концом строки. Произвольная подстрока `secret-ignore` внутри
данных подавлением не считается.

### Вывод и маскирование

Сырой diff, исходная строка и незамаскированный кандидат никогда не выводятся в
stdout, stderr, verbose, panic и сообщения об ошибках. В `v0.1.0` snippets
полностью отсутствуют. Scanner передаёт reporter только rule ID, путь, номер
строки, уровень риска и уже замаскированное значение. Значения длиной до
8 символов скрываются полностью; у более длинных остаются только первые и
последние два символа. Опциональные безопасные snippets переносятся в `v0.1.1`.

### Ограничения ресурсов

Размер staged blob ограничен 2 MB, длина строки — 5000 символов, длина
entropy-кандидата — 512 символов, общее время — 1500 ms. При превышении любого
лимита сканирование не считается полным и завершается кодом `2`. Пользователь
может явно исключить заведомо безопасный generated-файл через конфигурацию.
Ни один обязательный detector молча не отключается: режим Lite Mode в `v0.1.0`
отсутствует.

### Exit codes и потоки вывода

- `0` — проверка полностью завершилась, блокирующих находок нет;
- `1` — найден HIGH или блокирующий MEDIUM secret;
- `2` — Git, конфигурация, parser, timeout или другая системная ошибка.

Обычный отчёт направляется в stdout, предупреждения и системные ошибки — в
stderr. Pre-commit hook блокирует коммит при кодах `1` и `2`. Пользователь может
осознанно обойти локальный hook через `git commit --no-verify`; поэтому инструмент
не заменяет CI и не защищает уже существующую историю репозитория.

### Установка и удаление hook

Путь hook определяется через `core.hooksPath`, а при его отсутствии — через
`git rev-parse --git-path hooks`; это покрывает linked worktrees. Все пути
передаются без shell-интерполяции. Wrapper — POSIX `sh`, что совместимо с Git for
Windows, и получает права `0755` там, где файловая система поддерживает режимы.

Если pre-commit отсутствует, создаётся wrapper с уникальным marker и абсолютным,
shell-quoted путём текущего бинарника. Если marker уже принадлежит сканеру,
wrapper безопасно обновляется. Для чужого hook сначала рядом создаются полностью
записанный wrapper-temp, marker metadata и hash исходного hook; устанавливаются
права и выполняется sync. Затем исходный hook атомарно переименовывается в
`pre-commit.git-secret-scanner-legacy`, а temp — в `pre-commit`. При коллизии или
ошибке выполняется rollback, а существующий hook остаётся рабочим. Следующий
`install` умеет завершить или откатить прерванную транзакцию по marker metadata.

Wrapper находит legacy-hook через `HOOK_DIR=$(dirname "$0")`, сначала запускает
его и сохраняет ненулевой код, затем запускает сканер. Одинарные кавычки в
абсолютном пути бинарника экранируются по правилам POSIX shell. Недоступный или
перемещённый бинарник блокирует commit как системная ошибка.

`uninstall` удаляет только marker-owned wrapper. Legacy-hook восстанавливается
только если его имя и SHA-256 совпадают с marker metadata; его исходные права
также восстанавливаются. Если wrapper изменён вручную или владение нельзя
доказать, команда ничего не удаляет и возвращает понятное предупреждение.

## План трёхдневного релиза

### День 1 — рабочее ядро

Создать Go-модуль и CLI, реализовать получение staged diff, встроенные
regex-правила и коды завершения. К концу дня сканер должен находить известный
секрет в добавленной строке и блокировать коммит.

Ориентир — 4–5 атомарных коммитов: инициализация, CLI, diff parser, набор правил
и первая интеграция. Число коммитов не является критерием приёмки.

### День 2 — точность и безопасность

Добавить энтропию, классификацию токенов, конфигурацию, allowlist,
`secret-ignore`, маскирование и тесты граничных случаев. К концу дня инструмент
должен быть безопасен для реального локального использования.

Ориентир — 5–7 атомарных коммитов по отдельным проверяемым возможностям. При
дефиците времени нельзя сокращать маскирование, staged-only и fail-closed тесты.

### День 3 — установка и публикация

Добавить безопасную установку hook, удаление hook, CI, кроссплатформенную сборку,
README, демонстрацию и release workflow. После зелёного CI создать тег `v0.1.0`
и GitHub Release.

Ориентир — 5–7 атомарных коммитов, включая документацию, CI и release metadata.
Benchmark и GoReleaser могут перейти в `v0.1.1`; hook safety, тесты partial
staging и кроссплатформенная сборка обязательны.

## Стратегия GitHub Contributions

Коммит создаётся только для одного законченного изменения. Он должен иметь
понятное имя, проходящие тесты и возможность независимого отката. Временные,
пустые и искусственно раздробленные коммиты не используются.

Чтобы contribution засчитался:

- email автора должен быть связан с GitHub-профилем;
- итоговый коммит должен попасть в default branch;
- работа ведётся в самостоятельном репозитории, а не в fork;
- feature-ветки регулярно вливаются без squash, если важно сохранить отдельные
  осмысленные коммиты;
- push выполняется в день работы, без подмены дат.

Несколько коммитов за день увеличивают число contributions, но окрашивают одну
клетку календаря. После быстрого релиза регулярность создаётся обновлениями
`v0.1.x` или переходом к следующему полезному мини-проекту.

## Проверка качества

Перед `v0.1.0` должны пройти:

- unit-тесты правил, энтропии, маскирования и конфигурации;
- интеграционные тесты staged diff и partial staging;
- тест установки и удаления hook во временном репозитории;
- тесты на отсутствие открытых секретов в stdout и stderr;
- сборка `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`,
  `windows/amd64` и `windows/arm64`;
- архивы `.tar.gz` для Linux/macOS, `.zip` для Windows и файл SHA-256 checksums;
- ручная демонстрация успешного и заблокированного коммита.

## Критерий завершения

Релиз считается готовым, когда новый пользователь может скачать бинарник,
установить hook одной командой, увидеть блокировку тестового секрета и удалить
hook без повреждения существующей конфигурации Git.
